## Context

BeyondTheLoop is a Next.js brand + pre-sell site (see SPEC §1). L0 laid the
foundation (incl. the repository ports `SubscriberRepository` + `PurchaseRepository`
as TS interfaces in `src/types/repositories.ts`, and the `src/lib/{email,payments,analytics}`
barrels — empty in L0); L1 built the design system; L2 the Deck (`/deck`) + the
client `EmailCaptureForm`; L3 the landing page `/` (sections, typed content, the
persistent "Get the Kit" CTA, the Final-CTA `EmailCaptureForm`). Through L3,
**nothing is wired to a server**: the capture form is client-validation-only and the
buy CTA is a placeholder href.

L4 builds the **pre-sell engine** — the first public, money-collecting launch
(SPEC §5). It implements the layered `controller → service → repository → adapter`
flows from SPEC §4: email capture (browser → Loops) and the money path
(checkout → Lemon webhook → record Purchase → tag founding → analytics → instant
Harness Starter Kit download). All external services sit **behind the existing ports
as adapters** (`LoopsAdapter`, `LemonSqueezyAdapter`, `AmplitudeAdapter`).

**CRITICAL CONSTRAINT — the build must pass WITHOUT real API keys.** Adapters read
`process.env.*` **at request/runtime**, never at module-eval / build / typecheck
time. A typed env loader (Zod) validates env **lazily** (on first use in a request),
not at import. A `.env.example` lists every required key. No real key is ever
required for `pnpm install && pnpm lint && pnpm exec tsc --noEmit && pnpm build` to
be green, and no `.env*` file is committed.

**Done when:** the full gate is green **with no real keys present**; the
`/api/subscribe` and `/api/webhook` routes + controllers/services/adapters compile;
the email-capture form is wired (lead tag); the Lemon checkout + webhook
(verify signature → record Purchase → tag founding → analytics) + thank-you page
with an instant (placeholder) Harness Starter Kit download exist; the legal pages
exist; the funnel events are instrumented end-to-end. (Real end-to-end purchase is
verified manually by the user with real keys.)

## Locked decisions

1. **Layered ports & adapters (ADR-0002):** `app/api route → Controller (Zod
   validate, shape) → Service (business rules) → Repository (interface) → Adapter`.
   **No pure pass-through files** — every layer does a real job. Services depend on
   the repository **interfaces** in `src/types`, never on a concrete adapter.
2. **Adapters behind the existing ports, in `src/lib/*`:** `LoopsAdapter`
   implements `SubscriberRepository` (`src/lib/email/`); `LemonSqueezyAdapter`
   implements `PurchaseRepository` (`src/lib/payments/`); `AmplitudeAdapter`
   implements a new `AnalyticsClient` port (`src/lib/analytics/`). The
   `AnalyticsClient` interface is **added to `src/types/repositories.ts`** in the
   adapters epic (it does not exist yet). ([ADR-0002](../adr/0002-layered-architecture-with-repository-ports.md))
3. **Lemon Squeezy is the Merchant of Record (ADR-0003):** it is the legal seller
   and remits global VAT/GST; the app depends on `PurchaseRepository`, not on Lemon
   directly. Checkout is Lemon-hosted; the webhook **verifies the Lemon signature**
   before recording anything.
4. **No accounts / no auth (ADR-0004):** checkout takes email + card only; access is
   email-based. The Kit downloads instantly on the thank-you page; the bundled
   Screencast ships later via a signed/expiring email link (L6) — no login.
5. **Build green without real keys (CRITICAL):** adapters read `process.env.*` at
   **runtime**; the typed env loader (Zod) validates **lazily** on first use, never
   at import/module-eval. `.env.example` lists every key. No real key is required at
   build/typecheck time; no `.env*` is committed or read by the build.
6. **The Harness Starter Kit artifact is a PLACEHOLDER in L4:** the real kit contents
   are packaged later (SPEC §6 open item). Ship a clearly-labeled placeholder artifact
   (e.g. `public/harness-starter-kit/` with a README stub, zipped/stubbed) so the
   thank-you download route compiles and serves *something*; the spec notes real kit
   contents are added later. (CONTEXT.md: the Kit is the paid hero — the placeholder
   is explicitly temporary.)
7. **Tokens only — no hard-coded design values** on any new UI (thank-you, legal
   pages): the no-hard-coded-values ESLint rule applies to `src/components/**`; reuse
   L1 components. ([ADR-0005](../adr/0005-bespoke-atoms-with-radix.md))
8. **Allowed new deps:** the provider SDKs/clients as needed (e.g. Loops client,
   Lemon Squeezy client/`@lemonsqueezy/lemonsqueezy.js`, Amplitude Node SDK) **and**
   `zod` (already in the stack) for env + input validation. Prefer thin `fetch`-based
   adapters over heavy SDKs where reasonable; flag any heavy dep. No MUI/shadcn.

## Public APIs

```ts
// src/types/repositories.ts — ADD (alongside SubscriberRepository, PurchaseRepository):
export interface AnalyticsClient {
  track(event: AnalyticsEvent, props?: Record<string, unknown>): Promise<void>;
}

// src/lib/analytics/events.ts — the funnel events (SPEC §4)
export type AnalyticsEvent =
  | 'deck_slide_viewed'
  | 'deck_completed'
  | 'email_signup'
  | 'checkout_started'
  | 'purchase_completed';

// src/lib/env.ts — LAZY, runtime-only typed env (Zod). MUST NOT validate at import.
export function getEnv(): {
  LOOPS_API_KEY: string;
  LEMONSQUEEZY_API_KEY: string;
  LEMONSQUEEZY_STORE_ID: string;
  LEMONSQUEEZY_VARIANT_ID: string;        // the founding-price variant
  LEMONSQUEEZY_WEBHOOK_SECRET: string;
  AMPLITUDE_API_KEY: string;
  // ...any others; all read from process.env at call time, parsed once + memoized.
};

// src/lib/email/LoopsAdapter.ts          implements SubscriberRepository
// src/lib/payments/LemonSqueezyAdapter.ts implements PurchaseRepository + :
//   createCheckout(opts: { email?: string; offerId: string }): Promise<{ url: string }>;
//   verifyWebhookSignature(rawBody: string, signature: string): boolean;
// src/lib/analytics/AmplitudeAdapter.ts   implements AnalyticsClient

// src/server/controllers/SubscribeController.ts
//   handle(input: unknown): Promise<{ ok: true } | { ok: false; error: string }>  // Zod-validates { email }
// src/server/services/SubscribeService.ts
//   subscribe(email: string): Promise<void>  // dedupe -> upsert + addTag "lead" -> analytics email_signup
// src/server/controllers/PurchaseController.ts
//   handleWebhook(rawBody: string, signature: string): Promise<...>  // verify sig, validate payload
// src/server/services/PurchaseService.ts
//   recordPurchase(p: Purchase): Promise<void>  // record -> addTag "founding" -> analytics purchase_completed

// POST /api/subscribe   -> SubscribeController -> SubscribeService -> LoopsAdapter + AmplitudeAdapter
// POST /api/webhook      -> verify Lemon sig -> PurchaseController -> PurchaseService -> Lemon/Loops/Amplitude adapters
// POST /api/checkout     -> LemonSqueezyAdapter.createCheckout (founding price from offers.ts) -> { url }
```

Adapters are constructed via small factories that pull config from `getEnv()` **at
call time** (inside the request handler), so importing a module never touches a key.

## Architecture by concern

- **Lazy env (the build-without-keys guarantee):** `src/lib/env.ts` reads
  `process.env.*` and validates with Zod **inside `getEnv()`**, memoizing after the
  first successful parse. Nothing validates at module top-level. Adapters/factories
  call `getEnv()` from within request handlers only. Result: `pnpm build` / `tsc` /
  `lint` never require a key; a missing key fails **at request time** with a clear
  error, not at build time. `.env.example` documents every key (no values).
- **Email capture flow (SPEC §4.1):** `POST /api/subscribe` → `SubscribeController`
  (Zod-validates `{ email }`, shapes the response) → `SubscribeService` (dedupe via
  `findByEmail`, `upsert` + `addTag('lead')`, fire `email_signup` analytics) →
  `LoopsAdapter` (`SubscriberRepository`) + `AmplitudeAdapter` (`AnalyticsClient`).
  The L1 `EmailCaptureForm` submit is wired to this route (client validation stays;
  it now POSTs).
- **Money path (SPEC §4.2):** the buy CTA opens a Lemon-hosted checkout created by
  `POST /api/checkout` → `LemonSqueezyAdapter.createCheckout` at the **founding price
  read from `offers.ts`** (fires `checkout_started`). On payment, Lemon calls
  `POST /api/webhook`: the route reads the **raw body**, `PurchaseController` (via
  `LemonSqueezyAdapter.verifyWebhookSignature`) **verifies the Lemon signature before
  anything else**, validates the payload, then `PurchaseService` records the
  `Purchase` (`PurchaseRepository`), tags the Subscriber `founding`
  (`SubscriberRepository`), and fires `purchase_completed` (`AnalyticsClient`).
- **Thank-you + instant Kit (placeholder):** `src/app/thank-you/page.tsx` offers the
  **instant Harness Starter Kit download** — in L4 a **clearly-labeled placeholder
  artifact** under `public/harness-starter-kit/` (a README stub / zipped stub) so the
  route compiles and serves something. Real kit contents are added later (SPEC §6).
  Email-based access, no login (ADR-0004).
- **Legal pages:** `/terms`, `/privacy` (with the Amplitude EU-consent note),
  `/refund-policy` (30-day no-questions) — static pages reusing L1 components,
  token-only.
- **Analytics instrumentation (funnel, SPEC §4):** `deck_slide_viewed` +
  `deck_completed` fire from the L2 deck client (the player reports progress);
  `email_signup` from the subscribe flow; `checkout_started` from checkout creation;
  `purchase_completed` from the webhook. All go through the `AnalyticsClient` port /
  `AmplitudeAdapter`; event names live in `src/lib/analytics/events.ts`.
- **No-pass-through (ADR-0002):** controllers validate + shape; services hold the
  rules (dedupe, tag ordering, side-effect sequencing); adapters do the I/O. No empty
  forwarding shells. If a layer would do nothing for a flow, it is omitted.
- **Verification:** no test framework, no CI. The driver runs `LEAN_GATE`
  (`pnpm install && pnpm build`) after every epic and `VERIFY_GATE`
  (`pnpm install && pnpm lint && pnpm exec tsc --noEmit && pnpm build`) on the last
  (verify) epic — **all with no real keys present**. Final functional verification is
  **manual**: the user runs the signup + checkout→webhook→access paths with real keys.

## Per-epic specifications

Each epic is one fresh session = one commit, sized to the ~70k working-token
heuristic. The bd issue (`bd show <id>`) holds the full
CONTEXT/STEPS/ACCEPTANCE/HARD-RULES; this is the contract summary. The flows are
split so each session owns one coherent slice; **a dedicated verify epic is last**
(this is the launch layer — the end-to-end gate warrants its own pass).

### epic-0 — adapters
Add the `AnalyticsClient` port to `src/types/repositories.ts`. Build `src/lib/env.ts`
(typed Zod env loader, **lazy/runtime only — never validates at import**). Build
`LoopsAdapter` (`SubscriberRepository`, `src/lib/email/`), `LemonSqueezyAdapter`
(`PurchaseRepository` + `createCheckout` + `verifyWebhookSignature`,
`src/lib/payments/`), `AmplitudeAdapter` (`AnalyticsClient`, `src/lib/analytics/`),
each reading `process.env.*` via `getEnv()` at call time; extend the three lib
barrels. Create `.env.example` listing every required key (no values) and
`src/lib/analytics/events.ts` (the funnel event union). **Build must be green with no
keys present.**
**Commit:** `l4 epic-0 adapters: loops, lemonsqueezy, amplitude + lazy env loader + .env.example`

### epic-1 — subscribe-flow
Build `SubscribeController` (Zod-validate `{ email }`, shape response) +
`SubscribeService` (dedupe via `findByEmail`, `upsert` + `addTag('lead')`, fire
`email_signup`) in `src/server/*`; extend the controller/service barrels. Add
`POST /api/subscribe` (`src/app/api/subscribe/route.ts`) wiring controller → service →
`LoopsAdapter` + `AmplitudeAdapter`. **Wire the L1 `EmailCaptureForm` submit to POST
`/api/subscribe`** (keep client validation). No layer is a pass-through.
**Commit:** `l4 epic-1 subscribe-flow: subscribe controller+service, /api/subscribe, wire email form`

### epic-2 — checkout+webhook
Add `POST /api/checkout` (or a server action) creating a Lemon checkout at the
**founding price from `offers.ts`** (fire `checkout_started`); point the buy CTAs
(L3 Navbar + sections, L2 deck end-CTA) at it. Add `POST /api/webhook`
(`src/app/api/webhook/route.ts`) reading the **raw body**, verifying the Lemon
signature (`LemonSqueezyAdapter.verifyWebhookSignature`) **before anything else**, via
`PurchaseController` → `PurchaseService` (record `Purchase` → `addTag('founding')` →
fire `purchase_completed`). Build `src/app/thank-you/page.tsx` with the **instant
Harness Starter Kit download** served from a **clearly-labeled PLACEHOLDER artifact**
`public/harness-starter-kit/` (README stub / zipped stub) so the route compiles.
**Commit:** `l4 epic-2 checkout+webhook: lemon checkout, /api/webhook, thank-you + placeholder kit download`

### epic-3 — legal
Build the static legal pages reusing L1 components, token-only: `/terms`,
`/privacy` (include the **Amplitude EU-consent note**), `/refund-policy` (the **30-day
no-questions** refund). Link them from the Footer.
**Commit:** `l4 epic-3 legal: terms, privacy, refund-policy pages`

### epic-4 — analytics
Instrument the funnel end-to-end through the `AnalyticsClient` port: `deck_slide_viewed`
+ `deck_completed` from the L2 deck client (player progress), `email_signup` (subscribe),
`checkout_started` (checkout creation), `purchase_completed` (webhook). Ensure every
event flows via `AmplitudeAdapter`, with names from `src/lib/analytics/events.ts`, and
that client-side tracking respects the no-keys-at-build rule (public key handling at
runtime). No raw analytics calls scattered in components — funnel through the port.
**Commit:** `l4 epic-4 analytics: instrument deck/email/checkout/purchase funnel events`

### epic-5 — verify  (final epic — carries the gate)
Confirm the whole pre-sell engine compiles and lints **with no real keys present**:
run the full gate `pnpm install && pnpm lint && pnpm exec tsc --noEmit && pnpm build`.
Confirm `.env.example` lists every key the env loader requires; confirm no `.env*` is
committed and the build never reads a real key; confirm the placeholder Kit artifact
exists and the thank-you route serves it; append a short **Verification report** to
this spec (the only allowed edit to the frozen spec). As the last epic the driver runs
`VERIFY_GATE` here; **final functional verification is manual** — the user runs the
signup + checkout→webhook→access paths with real keys (see checklist).
**Commit:** `l4 epic-5 verify: full gate green without keys + verification report`

## Risk register

| Risk | Impact | Mitigation |
|---|---|---|
| **A key validated at import breaks the build with no keys** (the CRITICAL constraint) | red build/typecheck in CI / on a fresh clone | Lazy `getEnv()` — Zod parse happens **inside** the function at request time, memoized; adapters/factories call it only in handlers; nothing top-level reads a key. The verify epic explicitly runs the gate with no keys. |
| Webhook signature verified after (or not before) recording | a forged webhook records a fake Purchase | `verifyWebhookSignature(rawBody, signature)` is the **first** thing the webhook route does; the route reads the raw body (not parsed) for the HMAC; reject before any controller/service work. |
| Provider SDKs heavy / drift vs Next 16 / edge runtime | dep bloat, build red | Prefer thin `fetch`-based adapters; if an SDK is used, run adapters on the Node runtime (route `runtime = 'nodejs'`); flag any heavy dep before adding. |
| Reading the raw body in a Next 16 App Router route handler for the HMAC | signature mismatch | Use `await req.text()` (raw) in `/api/webhook`; do not `req.json()` before verifying. |
| **The real Harness Starter Kit does not exist yet** | nothing to deliver on the money path | Ship a **clearly-labeled placeholder artifact** (`public/harness-starter-kit/README`, stub/zip) so the route compiles + serves; the spec + the artifact both say "placeholder — real contents added later" (SPEC §6 open item). |
| Funnel events scattered as raw analytics calls in components | un-portable, EU-consent risk | All events go through the `AnalyticsClient` port / `AmplitudeAdapter`; names centralized in `events.ts`; privacy page carries the EU-consent note. |
| epic-2 (checkout+webhook) is the heaviest — checkout creation + signature-verified webhook + thank-you + placeholder kit in one session | budget overrun / red gate | The adapters (epic-0) already hold `createCheckout` + `verifyWebhookSignature`, so epic-2 wires routes + thank-you on top; if it overruns, split checkout (route + CTA wiring) from webhook (route + thank-you + kit). |
| Accidentally committing a `.env` or reading one at build | leaked secret / build coupling | `.gitignore` already ignores `.env*`; only `.env.example` (no values) is committed; CLAUDE.md forbids reading `.env*`. |
| bd hooks auto-commit `.beads/` | noise, not failure | Expected and tolerated per the task brief. |

## Verification

> Appended by epic-5 (verify) — the only sanctioned edit to this frozen spec.
> Records the static verification of the keyless-build guarantee and the layered
> flows, plus the manual end-to-end steps the operator runs with real keys. The
> automated `VERIFY_GATE` (`pnpm install && pnpm lint && pnpm exec tsc --noEmit
> && pnpm build`, **with no real keys present**) is executed by the Ralph driver
> after this epic.

### Keyless-build guarantee — verified statically

- **Env is lazy.** `src/lib/env.ts` defines the Zod schema at module scope but
  reads `process.env` and validates **inside `getEnv()`** only, memoizing the
  result. No top-level `getEnv()` / `process.env` access, so import / `tsc` /
  `build` never need a key; a missing key throws a clear, **value-free** error at
  request time naming only the missing key(s).
- **Adapters defer to runtime.** `LoopsAdapter`, `LemonSqueezyAdapter`, and
  `AmplitudeAdapter` each call `getEnv()` at **call time** inside their methods
  (verified: `LOOPS_API_KEY`, `LEMONSQUEEZY_API_KEY/STORE_ID/VARIANT_ID/
  WEBHOOK_SECRET`, `AMPLITUDE_API_KEY` are all dereferenced inside methods, never
  at module eval). Route handlers build adapters via factories, so importing a
  route touches no key.
- **No secret in the repo.** Only `.env.example` and `src/lib/env.ts` match
  `env` in `git ls-files` — no `.env` / `.env.local` is committed. `.env.example`
  lists exactly the six keys the loader requires (Loops; Lemon API/store/variant/
  webhook-secret; Amplitude) with empty values and explanatory comments.

### Layered flows — no pass-through (ADR-0002)

- **Subscribe:** `POST /api/subscribe` → `SubscribeController` (Zod-validates
  `{ email }`, shapes the result) → `SubscribeService` (dedupes via `findByEmail`,
  `upsert` + `addTag('lead')`, fires `email_signup`) → `LoopsAdapter` +
  `AmplitudeAdapter`. The L1 `EmailCaptureForm` POSTs to `/api/subscribe`
  (client validation retained).
- **Money path:** `POST /api/checkout` → `LemonSqueezyAdapter.createCheckout` at
  the **founding price from `offers.ts`**, fires `checkout_started`; buy CTAs
  (`CheckoutButton`) point at it. `POST /api/webhook` reads the **raw body** via
  `req.text()` and verifies the Lemon `x-signature` HMAC **first** —
  rejecting forged requests with 401 **before** any controller/service work —
  then `PurchaseController` (validate + shape, records only on `order_created`) →
  `PurchaseService` (record `Purchase` → `addTag('founding')` →
  `purchase_completed`).
- Each layer does real, distinct work; no empty forwarding shells.
